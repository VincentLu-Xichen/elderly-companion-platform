## 1. 先确定职责、数据与时序

本项目的主要工程问题是：**Agent 如何把一次回答转成可追踪的状态更新，再据此调整下一步，并把相关成果传递给后续课程？** CBT 提供课程配置和案例，不要求用户承担课程内容研究。

| 部件 | 负责什么 | 谁决定或校验 |
| --- | --- | --- |
| `LessonSpec` | 本课目标、所需输入、记录字段、示例、阶段、完成条件 | 开发者维护版本化配置 |
| `LearningState` | 已收集/已确认的记录、缺少字段、阶段和引用来源 | 模型提议摘录，程序校验并更新；本人确认单独记录 |
| `ReflectionRecord` | 被触发时结合既有总结与新增交互，保留简短观察、未解决事项、下一步策略 | 模型提出，程序核对来源和策略范围；不绑定每轮调用 |
| `TriggerDecision` | 根据配置和可追溯的回答信号，决定此时是否需要更新反思 | 程序执行触发策略，记录理由；策略优劣待实验 |
| Actor / 教学 Prompt | 使用本课配置、最新状态和获准策略，生成下一条自然回复 | 模型生成，程序校验返回格式及允许的行为 |
| Controller / 状态机 | 接受状态补丁、确定允许的动作和阶段、处理本人操作 | 程序执行，模型不能直接确认、授权或完成课程 |
| `CourseArtifact` | 在课末冻结本人确认的成果、出处与版本，供后课按需引用 | 程序生成；后课读取受本人选择和来源校验约束 |

Prompt 指导模型如何判断和表达；Schema 规定交换哪些字段；Controller 决定这些输出能造成什么状态变化。三者应一起定稿，具体措辞可随后迭代。

## 2. 区分记录粒度与反思粒度

- **Turn**：一次 Agent 指导与随后的用户回答，是基本交互记录单位。
- **Task step**：一个有明确目标和退出条件的子任务，例如补齐一个字段或完成一次例子辨认；可跨多个 turn，记录 `task_step_id`。不再将 step 固定等同于 turn。
- **Phase**：课内阶段，例如签到、示例、练习、核对。一阶段可以包含多个 task step。
- **Lesson**：一节课，含多个阶段；结束时生成可跨课引用的成果。

候选触发策略为不使用课内反思、每 turn、每 task step 结束、按回答事件触发。原论文在 ALFWorld 实验中也使用重复动作和轨迹过长等启发式触发；这支持将触发策略作为设计变量，但不能证明本项目的质量触发优于固定频率。[Reflexion 原论文，第 4.1 节](https://papers.nips.cc/paper_files/paper/2023/file/1b44b878bb782e6954cd888628510e90-Paper-Conference.pdf)

## 3. 每轮状态更新与可选反思分开

记 `S` 为可追踪的学习状态，`R` 为简短的反思记忆，`A` 为上一条指导，`U` 为本次回答。数据抽取和正常指导在所有实验条件中保留，单独改变反思触发策略。

```text
输入：旧状态、仍适用的旧反思、上一条指导、本次回答、课程/子任务配置
    ↓
常规轮次：提议原话补丁、任务反馈信号、阶段建议与回复草稿
    ↓
Controller：校验补丁、形成候选状态，执行 TriggerPolicy
    ↓
未触发：复核旧策略仍适用，校验常规回复后提交
已触发：Reflector 更新反思 → 校验 → Actor 根据新反思生成回复
    ↓
提交本轮状态、触发决定及实际发送的回复；等待下一次回答
```

触发时，新反思应影响尚未发送的下一条指导。常规草稿如果已经生成，就需要在反思后重新生成或采用明确标记的联合修订；不能将已经发送的回复事后记为使用了新反思。

已有总结主要由结构化状态表达，反思记忆补充“上一步采用什么策略、反馈如何、接下来怎样做”。二者不混写：重新总结不能将模型猜测覆盖成本人事实。

每个 turn 都记录触发决定，只有实际调用 Reflector 才产生新的反思事件；不触发不能伪装成模型返回了 `no_change`。被触发后仍允许 `no_change` 或 `insufficient_evidence`。暂停、确认等确定性操作由程序处理，安全暂停继续在模型调用前执行。

### 3.1 回答质量与 importance 的候选信号

这里的质量描述“回答对当前任务提供了什么证据”，不评价用户人格、能力或是否顺从 Agent。importance 暂定义为“这条反馈是否可能改变下一步指导或有效状态”，不预设固定权重。

| 信号 | 要检查什么 | 可能的反思用途 |
| --- | --- | --- |
| 任务适配与充分性 | 对应当前问题，已提供哪些必要信息；简短回答也可能充分 | 决定继续、核对，或只补问一个缺项 |
| 明确纠正/不理解 | 本人说记录有误、没听懂，或指导方式不合适 | 撤回旧推测或改变解释方式 |
| 新的相关信息 | 出现足以改变现有判断或计划的证据/偏好 | 更新策略，保留有效的指导方式 |
| 同一上下文的冲突 | 同一事件、字段、时间范围下，与已有信息不一致 | 先澄清冲突，不能按新旧次序直接选边 |
| 交互停滞 | 多轮仍缺同一信息、重复追问或同一解释无效 | 检查 Agent 的引导是否需要改变 |

回复长度、消极词数量、赞同 Agent、时间流逝都不能单独作为质量或 importance。未解决事项持续多久可作为策略陈旧/停滞的辅助信号，是否有用通过实验决定。

### 3.2 前后反差要结合问题解释

用户提出的“课内精神状态可能较稳定”作为待检验的工作假设保留，不将其写成系统事实。系统优先记录明确表达、任务反馈和具体事件，不为每个回答重新推断全局精神状态。

比较前后回答时记录问题意图、讨论事件、目标字段和时间范围。问开心事件与问担忧事件得到不同情绪词，不应自动视为矛盾；同一事件的叙述发生变化、本人明确表示当前状态变化，才值得进一步核对。缺少可比上下文时标记未知，避免单纯用情绪反差触发。

## 4. 反思记忆怎样滚动更新

- Reflector 使用本课经验证的摘要、前次反思，以及从上次反思以来仍相关的新交互与本次回答；按触发范围收集证据。按 task step 触发时不能只看最后一个回答，忽略该子任务的前几轮。
- 在线上下文只保留当前结构化状态和少量近期反思；完整 step 事件保留在加密审计中，不把历次反思无限拼接到 Prompt。
- 本人纠正优先于旧的推测；模型只能提出记录补丁。已确认记录的修改进入显式修订流程，不可被反思静默覆盖。
- 指导策略从白名单选择，例如澄清缺项、换口语解释、承认纠正、汇总供确认。策略映射为受控指令，不能直接将任意反思文本追加为高优先级规则。
- 同一课内允许有效策略影响下一步，不逐轮额外询问授权。课间事实引用与指导偏好迁移按各自适用规则处理，不能顺带读取其他课程的聊天原文。
- 每次记录反思依据及应用到哪条回复。后续反馈不足时，保留“未验证”，不声称策略有效。

## 5. 调用方式与失败语义也需公平比较

不再预设每轮双调用。逻辑上分开常规处理、触发决定、反思与最终回复生成；实际调用次数需要明确计量。

一个可审计的参考实现是：常规模型调用返回原话补丁、少量任务反馈信号与回复草稿；触发器复用这些信号。未触发时通常一次调用；触发时额外调用 Reflector 和 Actor，合计三次。这个代价必须如实记录。另一方案先提取信息再生成回复，可能产生每轮两次、触发时三次的成本；不在尚未验证时宣称按需反思一定省成本。

额外使用一个模型判断是否触发，也必须计入触发器成本。单次同时生成反思与修订回复可作为性能方案，但应标明联合生成；不能宣称回复读取了已经过服务端校验的新反思。比较触发策略时先固定调用拓扑，再单独研究合并调用，避免同时改变两个变量。

现有第 2 课的普通轮次一次调用、600 tokens 上限仍属于当前实现约束；新的调用拓扑需要独立课程/协议版本，不能悄悄套入第 1、2 课。

建议每 turn 使用同一个幂等键和处理租约，分阶段记录常规处理、触发决定、可选反思、最终回复与提交结果。用户消息先保存；触发后的反思校验失败时不生成基于无效反思的回复，失败重试保留候选及各阶段审计。未提交的候选不能作为成功进度。重试核对原输入、状态修订号、引用来源和策略版本，条件变化后使旧候选失效。最终回复提交后才记为反思已应用。

## 6. 结构化输出需要确认哪些内容

需要先确定数据含义、写入权和生命周期，而不只是要求模型“输出 JSON”。当前草案见[契约](contracts.md)。

- Reflector 可以提议什么事实摘录、反思和动作；哪些字段必须来自原话，哪些是模型假设。
- Controller 如何接受、拒绝、撤回和修订；阶段变化与课程完成由谁决定。
- Actor 接收什么状态，只返回哪些字段；界面只呈现回复、阶段与本人记录，反思短结论供开发与研究审查。
- 来源、版本、确认状态、缺失值和不确定如何表达；不能让模型必须编造完整答案。
- 哪些是本课临时工作记忆，哪些在本人确认后成为跨课成果。

生产实现时用单一 Pydantic 类型定义生成 Schema 和字段文档，避免 Prompt、解析器与接口分别维护而漂移。供应商严格 Schema 是格式约束，仍需业务校验与错误分支。[OpenAI 官方文档](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=chat)

## 7. Prompt 如何组织

采用稳定骨架加课程配置，草案见[Prompt 文件](prompts.md)：

1. 公共规则：角色、表达风格、数据来源、权限与安全边界。
2. 常规 Turn Prompt：每轮提议记录补丁、可追溯的任务反馈及普通回复。
3. Reflector Prompt：仅被触发时读取相关交互范围，更新简短反思和下一步策略。
4. Actor Prompt：触发后根据程序给出的有效新状态和反思重新生成下一条回复。
5. 课程/子任务配置：替换本课目标、字段、例子及退出条件，不为每课复制整个系统。

反思是可检验的短结论、证据引用和策略记录，不保存完整思维链。Prompt 的具体表达通过案例回归调整；职责、契约和版本先稳定。

## 8. 八课之间的数据联系

以下是课程配置层的依赖草案，不表示尚未实现的课程已经开放，也不强制按顺序解锁。每次只引用相关、有效且获准的成果；没有来源时允许新例子。

| 课次 | 主要可引用的输入 | 本课预期输出 | 后续用途 |
| --- | --- | --- | --- |
| 1：四要素 | 新的生活例子 | 事情、想法、心情、行为记录 | 给第 2 课表达练习及第 4 课行为练习提供案例 |
| 2：三栏 | 第 1 课相关记录或新例子 | 已确认的事情、想法、心情 | 给第 3 课辨认及第 6 课证据检查提供具体想法 |
| 3：思维习惯 | 第 2 课三栏；缺失时可选第 1 课 | 原想法、依据说明、分类候选与本人核对结果 | 给第 6 课提供待检查的问题；允许保留不确定 |
| 4：行为回应 | 第 1 课的情绪与行为；必要时本人重新说明 | 原有反应与替代回应计划 | 给第 5 课具体行动安排提供起点 |
| 5：活动/渐进面对 | 第 4 课计划或新目标 | 自主选择的行动路径与小步计划 | 后续收集实际尝试反馈，供第 8 课回顾 |
| 6：检查想法 | 第 2/3 课的具体想法与辨认记录 | 支持/不支持的信息、本人形成的新表述 | 给第 8 课整理可继续使用的方式 |
| 7：睡眠/放松 | 本人当前需求及获准引用的相关安排 | 自选练习与可行安排 | 给第 8 课整合日常计划 |
| 8：维持计划 | 本人选择回顾的前课成果和实际反馈 | 有来源的个人回顾与后续计划 | 形成结课成果，保留尚未验证或未尝试的项目 |

跨课传递包含两类内容：本人确认的成果，以及在新课仍适用且获准沿用的简短指导偏好。未经核对的推测和整段本课反思轨迹不默认迁移。第 3 课负责验证上述机制；课程素材保存在独立文件，保持工程设计与素材维护相互清楚。

## 10. 工程验收与比较

后续实施需先确定上述契约、Prompt 职责、调用拓扑与版本策略，再改运行代码。本轮仅修订可评审设计，不运行模型实验；触发频率、信号权重和阈值均未确定。

关键验收：每轮正常记录；触发理由有证据；触发后最终 Actor 读取的是有效新反思；不触发时不沿用过时策略；纠正后旧推测不再次进入有效状态；字段缺失时不跳阶段；模型不能自行确认或完成；重试不重复写入；各阶段失败可恢复并审计；摘要长度有界；课间引用符合归属和版本。

先比较四种触发策略：A 不使用课内反思，B 每 turn，C 每 task step 结束，D 根据质量/事件信号。所有条件使用相同的常规状态更新、可用原始反馈、模型、课程配置和记录来源；固定反思模板、调用拓扑及相同总预算上限，实际消耗作为结果记录。事件策略权重/阈值在开发案例上确定，保留未用于调参的评估案例。后续再比较时间/固定间隔辅助信号是否提供增益。

先用相同对话前缀成对评估下一步动作，检查纠正响应、无依据状态写入、重复提问和错误推进；这只能评估局部决策。若要评估完整课程，另做可复现的连续交互，不能从固定前缀比较直接推导整课收益。独立复核触发的误报/漏报，并记录触发率、各模块 token、总成本、延迟及反思过度改写正确状态的次数。

反思内容质量与触发策略分开研究：先固定反思模板比较触发，再在同一触发策略下比较简单总结与“问题依据→策略调整→之后核对”模板。课程作为工程测试场景，教学或临床价值不作为本轮设计成立的前提。

## 11. 可用于报告的表述

> 本次修订课程 Agent 的反馈架构，将反思触发策略与每轮结构化状态更新分离，并将 turn、子任务边界和回答事件触发列为待比较条件。系统依据有来源的任务反馈评估是否需要调整指导，区分问题变化与同一上下文的真实冲突。当前交付为设计及契约、Prompt 草案，尚未运行比较实验或确定最优触发方式。
